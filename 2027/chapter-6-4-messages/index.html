    6.4 Messages

    The base message is elaborated below into specific messages. From release 2027, 10 substantive messages and the Feedback Message are active; 5 FPR messages have been discontinued (see §4.3.11). The distinction between a direct and a layered order model has been dropped as of release 2027; see §4.2.

    Explanation: Administrator of Cohort and Investment Pools (ACB) — discontinued

    The ACB role has been discontinued as a separate actor in this overview. In practice this role is fulfilled by the BA or sometimes by the PUO. Because the ACB role no longer appeared as a separate party as of July 2026, the column has been removed from the matrix. Should the ACB role act as an explicit party again in the future, the message schema still allows for this through the existing messages. See GitHub issue #131.

    Explanation: role versus party. Table 12 is a role matrix and is generated from the data model. Messages 10 and 14 are sent by the BA role. That role can be fulfilled by the PUO; this does not make the PUO a second sender. For that reason, the PUO column for message 14 does not contain from. See GitHub issue #142.

    The Feedback Message has no fixed sender and receiver — it follows the message to which it responds — and therefore falls outside the generated rows.

    Note: Each receiving party/role receives its information directly from the sending party. Sending to parties/roles not mentioned in Table 12 is also direct. Received information is not forwarded to other parties. A message can therefore be sent to more than one receiver, each with its own endpoint and identification; see §2.4.

    Explanation: suffixes in the message diagrams on GitHub. An entity can occur in more than one position in a single message. In message 3, for example, financialTransaction.payment occurs directly under the scheme, under the cohort and under the investment portfolio. In the message diagrams on GitHub (the Wiki/Berichtenoverzicht and the folder MessageStructureView for each message), these positions are given a suffix, such as financialTransaction.payment_1. That suffix is a sequence number to keep the positions in the diagram apart, not a different entity type: the attribute entityType has the same value in every position (here payment). The suffix does not occur in the message itself; which position is meant follows from the parent entity. The sequence number is assigned per message, so the same suffix can denote a different position in another message. This manual does not show the suffixes: in the base message (§6.4.1), the message structures and the cross-reference table (§6.5), each position appears under its own parent entity.

    1. Assets (0001a)

    (4.2.1.1)

    		 Vermogen/
    Capital

    From 🡪 To

    From PUO to FM and BA/asset service provider.

    On a periodic (expected to be monthly) basis, the FM receives, for a pension provider, per scheme the total pension assets at the start of the period.

    In addition to the information at total level, the FM can also receive the pension assets per cohort. For example, for the age cohort 25-29 years, the total of the personal pension assets at the start can be received.

    With the cohort information, the FM can, if desired, make a total calculation and test the reconciliation with the information supplied at total/collective level against the policy of the fund. This is useful for a robust handover and audit trail, depending on agreements the parties make. In accordance with the policy of the pension provider, rebalancing may be desirable in the event of (large) deviations. In addition to the FM, this information can, if desired, also be provided to the BA/asset service provider, so that it too is able to carry out testing and reporting activities using the leading investment administration.
    SPR

    2. Cashflow (0001b)

    (4.2.1.3)

    		 Cashflow/
    Cashflow

    Inflow and outflow

    From 🡪 To

    From PUO to FM and BA/asset service provider.

    On a periodic (expected to be monthly) basis, the FM receives, for a pension provider, per scheme the inflow in the period and the outflow. In addition to total level, inflow and outflow can also be supplied per cohort.

    Besides premiums, value transfers and benefit payments, the inflow and outflow also contain the shifts between cohorts, where applicable. A cohort can also be a year of birth. The ‘cohort’ solidarity reserve, the ‘cohort’ compensation deposit and possibly other reserves will also be included.

    With the cohort information, the FM can, if desired, make a total calculation and test the reconciliation with the information supplied at total/collective level against the policy of the fund. This is useful for a robust handover and audit trail, depending on agreements the parties make. In addition to the FM, this information can, if desired, also be provided to the BA/asset service provider, so that it too is able to carry out testing and reporting activities using the leading investment administration.
    SPR

    3. Pension Projection (0001c)

    (4.2.1.3)

    		 Pensioenprojectie/
    PensionProjection

    Projected benefits

    From 🡪 To

    From PUO to FM, BA/asset service provider and LDI manager (see Figure 1, flow 1c, and Figures 8 and 9, steps F and G).

    On a periodic (the expectation is monthly) basis, the FM receives from a pension provider, per scheme and per cohort, the projected benefits based on the accrued assets for future periods.

    The data exchange also contains the cash flows to be hedged per scheme per future period. This is equal to the sum of the weighted projected benefits per cohort. The weighting factor is equal to the protection percentage per cohort. In this way a profile of the cash flows to be hedged is created. This exchange avoids misunderstandings regarding the cash flows to be hedged and can, if desired, introduce a check into the process.
    SPR

    4. Return Information (00002)

    (4.2.2.)

    		 Rendementsinformatie/
    ReturnOnInvestment

    Information need of the PUO

    From 🡪 To

    Information flow from BA/asset service provider to the PUO.

    To carry out the Solidarity Premium Scheme, the PUO periodically (expected to be monthly) needs information about the return achieved.

    Periodically, the PUO receives over the period, for a pension provider, per scheme and per portfolio, the value at the start of the period, the value at the end of the period and the return in portfolio currency and (where applicable) expressed as a percentage. The PUO is responsible for allocating returns to participants on the basis of portfolio returns. Optionally, pension assets, protection return and excess return can also be shared with the PUO per cohort in the scheme. Whether these optional elements are exchanged depends on the agreed roles and responsibilities between the cooperating parties.

    The principle is that the PUO is responsible for allocating returns, in accordance with the allocation rules set by the pension provider, to the personal pension assets of participants, the solidarity reserve, any compensation deposit and possibly other reserves.
    FPR

    5. Order Instruction (00541)

    (5.4.1.)

    		 Orderopdracht/
    Trade

    From 🡪 To

    Information flow from PUO to BA (see Figures 8 and 9, step A).

    This is the minimum set of data needed to be able to send an order to an order-processing party. It can also be used to carry out a switch.

    The PUO submits orders at the level of the investment product. The provider of the product carries out the ordering in the underlying investments itself. This may concern, among other things, listed and illiquid investments.

    6.4.1 Base Message

    The base structure for messages (transaction) shows the hierarchical relationships between different entities in the data model. The entities and entity types form a coherent hierarchy. By definition, a hierarchy must be applied in the messages to be exchanged, and the structure of the transaction forms the basis for this. Among other things, the structure indicates which child entity belongs to which parent entity.

    The column "Cardinality" shows the minimum and maximum number of times that entity can occur. V (mandatory, Dutch verplicht) or O (optional) indicates whether an entity.entitytype must or may occur.

    The base message is a generalisation over the individual messages and not a message in itself. It shows every position in the hierarchy that occurs in at least one message. An entity that can occur in more than one position therefore appears more than once, each time under its own parent entity: financialTransaction.payment occurs directly under the scheme, under the cohort and under the investment portfolio. Not every message has every position. Which positions a message contains, and with which cardinality, is shown in the message structure of that message (§6.4.2 onwards); this may differ from this table.

    1) Per party.sender, multiple party.contact are possible

    2) Per party.pensionProvider, one or more pension.schemes occur

    3) Per pension.scheme, exactly one financialInformation.reportingPeriod occurs; message 15 has no reporting period (§6.4.11)

    APF ring-fenced compartments: two common scenarios

    For a General Pension Fund (APF) with multiple ring-fenced compartments (kringen), there is one pension.scheme per ring-fenced compartment under one party.pensionProvider. Two scenarios exist side by side in the market:

    Scenario 1 — Ring-fenced compartment has its own PUV code Each ring-fenced compartment is identified by its own puvCode in party.pensionProvider. Buffer capital above ring-fenced compartment level is handled pragmatically through a cohort construction, because no separate PUV code exists for it.

    Scenario 2 — Ring-fenced compartment has no PUV code of its own There is one PUV code at APF/provider level. The distinction between ring-fenced compartments runs via references at pension.scheme level.

    Both scenarios are supported by the standard. Parties lay down the chosen approach in agreements between chain parties (TOM / SLA). See GitHub issue #114.
